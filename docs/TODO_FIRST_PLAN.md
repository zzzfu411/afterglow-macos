# Moro 待办体验改造计划

2026-10-08 · 基于主分支 `cb4bd20` 与本机 Moro 0.6.1 的原始方案

> 0.7.0 已按本方案实施主要功能。本文保留当时的问题与验收目标，不代表当前缺陷清单；实际交付和未验证范围见 [实施记录](TODO_IMPLEMENTATION.md)、[QA](../QA.md) 与 [资源测量](PERFORMANCE.md)。

Moro 的下一步定位：**一款轻巧的 Mac 待办应用，需要时，从事项直接开始一段专注。** 打开应用先看到要做的事；记录、整理、完成都不依赖计时。计时保留在同一个工作流中，避免在清单和时钟之间来回切换。

本轮检查了原生主窗口、新增及截止日期表单、待办与计时状态模型、存储、通知、快捷键、窗口布局及现有测试；竞品资料来自官方页面。未改动真实待办或安装版。下述竞品比较是功能与交互研究，不是同机性能横评；视觉判断与优先级是本项目的设计建议。

## 当前体验的问题

| 环节 | 当前行为与依据 | 对用户的影响 | 优先级 |
| --- | --- | --- | --- |
| 视觉主次 | `FocusWindow` 主内容是大号计时器；事项放在 160–340 pt 侧栏 | 为了看清事项必须扩大窗口，主要空间却仍留给时钟 | P0 |
| 快速记录 | 新增替换整块侧栏；预计时长必须为 1–180 分钟，默认 25 | 看不到原清单，暂时不知道时长也必须接受一个估计 | P0 |
| 选择与完成 | 行首圆圈和标题负责“选择专注”；完成藏在更多菜单 | 圆圈容易被理解为完成框；日常最高频操作多一层 | P0 |
| 撤销与恢复 | 已支持完成撤销、已完成事项恢复；撤销仅保留最近一次，未接入系统待办操作 UndoManager | 误操作恢复有入口，但与 Mac 的 ⌘Z 预期不一致；删除没有回收区 | P0 |
| 计时与浏览 | 运行或暂停时整行选择专注按钮禁用 | 浏览事项与切换当前专注绑定，清单像一个计时设置面板 | P0 |
| 截止日期 | 开启后同时显示日期和时间；无仅日期语义；按截止时间排序 | “今天做”和“今天必须交”不能区分；非紧急任务不好安排 | P1 |
| 提醒 | 系统通知只覆盖专注/休息到点；待办截止日期不调度通知 | 用户可能将“截止时间”误认为届时会提醒 | P1 |
| 清单组织 | 单清单，无独立今天/收件箱/搜索/自定义清单/手动排序 | 事项增加后很难找到下一件事，也难区分工作与生活 | P1 |
| 容量与归档 | 100 项上限包含已完成事项 | 长期使用会被迫删除历史，不能通过这一限制实现产品的低内存目标 | P0 |
| 任务与时长 | 事项估计直接成为本轮倒计时；整张清单是总时长的一次倒计时 | 一件长任务容易变成几小时计时；整张清单也没有逐项推进 | P1 |
| 回看 | 专注日志保存标题快照，不保存事项 ID；待办无完成时间 | 无法可靠汇总某项任务的专注记录，重命名后更难对应 | P1 |
| 视觉材质 | 全窗口使用 behind-window HUD 材质并强制 active | 大面积正文受背景影响；层次和阅读稳定性不够适合长清单 | P0 |
| 扩展基础 | 单份 JSON 绑定待办、计时和历史；操作在主模型调用同步读写，任意共享状态变更都请求刷新小组件 | 目前小数据尚可，增加清单规模、搜索和自动保存前需要拆清边界 | P0 |

P0 是第一批改造必须覆盖的内容，P1 是使待办能承担日常使用的后续内容。表中的源码问题不全部等于已复现的运行故障。例如存储规模风险需要大数据量实测，不能据此声称当前已卡顿。

已有基础应继续保留：原生 SwiftUI/AppKit、离线本地数据、稳定事项 ID、原子写入与文件锁、事件驱动的文件监听、单次到期计时器、已有误标恢复、可选 deadline、⌘B 和系统外观跟随。

## 从竞品借鉴什么

| 参照 | 已核实的做法 | Moro 的取舍 |
| --- | --- | --- |
| Apple 提醒事项 | 列表、智能列表和子任务构成组织基础；部分功能依赖更新后的 iCloud 提醒事项 | 学习原生列表、编辑与恢复习惯；先做好本机个人清单 |
| Things | 开始日期、deadline 和提醒有不同语义；额外字段按需展开 | 分清“安排在哪天”与“必须何时完成”，默认只露标题 |
| Todoist | 快速添加可逐步补充属性，桌面支持全局快速添加 | 先实现标题回车保存，再补菜单栏/全局录入；自然语言解析后置 |
| TickTick | 已把任务、番茄专注、日历、习惯和统计放在同一产品 | 待办加计时本身并不独特；Moro 需要在轻量、少步骤与 Mac 原生体验上做扎实 |

依据：[Apple 提醒事项指南](https://support.apple.com/en-ca/guide/reminders/welcome/mac)、[Things 的任务安排](https://culturedcode.com/things/support/articles/2803579/)、[Things 的按需详情](https://culturedcode.com/things/features/)、[Todoist 快速添加](https://www.todoist.com/help/todoist/features/use-task-quick-add-in-todoist-va4Lhpzz)、[TickTick 功能](https://ticktick.com/features)。

Moro 现有的开源、本地与原生实现是可信基础；“更省内存”“比竞品更高效”还需要测量。目标用户先聚焦在 Mac 上独立工作、希望把事情记下并开始执行的人。团队分配、云协作和复杂项目管理暂不进入主线。

## 推荐的窗口结构

采用两栏：**左侧导航，右侧清单**。事项离开窄边栏后，长标题、截止日期和编辑区域才有足够空间。首次打开展示今天；以后记住上次视图，空视图保留明确的新建入口。

- 左侧：收件箱、今天、接下来、全部；自定义清单在第二阶段加入。已完成与最近删除位于次级区域，也可从菜单和搜索访问。
- 中间：当前清单标题、添加入口、搜索；下面是普通任务行，没有重复的大卡片。
- 底部：只有开始专注后出现一条小控制栏。未计时时，正文不为大时钟预留空白。
- 详情：点击标题在原行展开；只展开当前事项，避免默认常驻第三栏。较长内容可打开独立详情。
- 紧凑窗口：折叠导航，保留完整清单；标题可切换清单。⌘B 和可见侧栏按钮都保留。

尺寸起点为默认 760 × 540 pt，侧栏理想宽度 184–220 pt，允许缩至约 160 pt。窄至约 560 pt 时折叠导航；单栏以 360 pt 宽为验证起点，最终最小值由内容测试决定。较宽窗口增加阅读空间，不放大时钟。侧栏用于顶层导航、支持隐藏和尺寸适配，符合 [Apple 侧栏指南](https://developer.apple.com/design/human-interface-guidelines/sidebars)。

### 每个位置只有一种主要含义

| 操作位置 | 行为 |
| --- | --- |
| 左侧完成框 | 标记完成；再次点击可恢复。扩大命中区，但不覆盖标题 |
| 标题/行正文 | 选中并展开详情，绝不隐式开计时或完成 |
| 右侧 ▶ | 为这项任务开始专注；首次使用记住的默认时长，旁边可改时长 |
| 更多菜单 | 移动、复制、删除等次要操作 |
| ⌘N、输入标题、回车 | 添加事项；估计时间、日期、备注都可留空；连续录入保持输入位置 |
| ⌘Z / ⇧⌘Z | 撤销/重做任务操作；在文字编辑器内仍优先处理文字撤销 |

完成后短暂保留反馈，再移入已完成；保留明确撤销入口和稳定的键盘焦点。删除进入最近删除，支持恢复。关闭详情保留已保存修改；未提交的新建内容不会因隐藏侧栏或切换清单丢失。中文输入法确认候选词不应误触发提交。

不再让空格在整个主窗口无条件控制计时。建议主窗口用 ⌘Return 开始/暂停当前专注，专注模式下才保留空格；文字输入期间均不截获。此调整随界面发布同步更新菜单与帮助。

## 待办的日期与组织规则

**四类信息分别处理：事项标题、计划日期、截止日期、估计时长。只有标题必填。**

- 计划日期回答“打算哪天做”。可一键加入今天，或选择将来某天。
- 截止日期回答“最迟何时完成”。支持只选日期，时间通过“添加时间”显式开启；不强行赋予 18:00。
- 提醒是独立的可选动作。只写 deadline 不默认发通知；提醒已开启时用铃铛状态表示，权限拒绝时保留任务并提示状态。
- 估计时长是任务规模，允许空值和超过三小时；专注时长是这一次投入多久。两者不能再自动等同。

“今天”显示安排到今天及尚未完成的往日计划，并显示今日到期与逾期事项。逾期分组仅在有内容时出现；任务改期只改计划日期，不默默推迟 deadline。日期型截止在本地日历日结束后才算逾期，精确时刻型按该时刻判断；跨午夜、夏令时和时区变化需要专门验证。

“接下来”按日期呈现计划与 deadline；同日同项去重并标明含义。“全部”及普通清单保留截止日期排序作为默认选项，无日期项在后；另提供手动排序。在自动日期排序下不允许看似拖动成功、随即又跳回原处。“今天”可先处理紧急分组，再手动调整其余事项。

第一版任务详情只放备注和上述可选字段。简单的一级步骤清单、重复任务随后加入；暂不引入多层项目、标签树、优先级矩阵及满屏统计。

## 把计时简化成清单的一部分

例子：某项任务估计 2 小时，用户可以先专注 25 分钟。计时结束后任务仍待办；用户决定继续、休息或标记完成。只有点完成框才改变待办状态。

1. 点事项的 ▶，开始一次专注。时长控件提供 15 / 25 / 45 分钟及直接输入，记住用户选择。
2. 底栏只保留事项名、剩余时间、暂停/继续、结束。点事项名回到对应任务，点展开进入可选的专注视图。
3. 计时期间仍可浏览、添加、搜索和编辑其他事项。当前计时与列表选择分别保存。
4. 若启动另一个事项，给出一次“结束当前并切换”确认，明确处理已投入时间；不静默覆盖本轮记录。
5. 到点显示轻量操作“再专注 / 休息 / 完成事项”，不强制进入休息。提前完成当前任务时结算本轮并提供撤销。

撤销完成只恢复待办状态，不自动重启已结算的计时，也不回退真实已投入时间。

现有“整张清单”总时长计时移出首页。逐项推进作为后续可选队列：每次只计一项，完成/跳过后点下一项；不自动替用户完成任务。迁移期间保留已开始的旧计时直到自然结束或用户结束。

菜单栏先保留当前专注控制，再增加快速录入。桌面小组件后续优先展示今天的少量事项与当前专注；签名、App Group 与实机安装验证是独立交付条件，不能把源码已存在当作小组件可用。

## Mac 视觉方向

**保留晨光 Logo 的识别度，把工作界面做得安静、清晰。**

- 使用系统字体 SF Pro / 苹方，正文约 13–14 pt，标题约 22–24 pt；日期与属性约 11–12 pt，避免目前 10 pt 截止文字成为重要信息的唯一入口。
- 系统语义色与用户强调色优先。主内容为稳定的浅色/深色阅读面，侧栏和工具栏使用对应原生材质；不为每行加毛玻璃或阴影。
- 留白集中在清单外边距和组间；任务行约 40–48 pt，内容自适应增高。长标题可换行并在详情看全文，不靠把窗口撑大。
- SF Symbols 统一线重；普通图标单色。逾期用文字加图标辨认，强调色只表示选中、当前专注或明确操作。
- 轻量选中背景、细分隔、稳定的工具栏与完成反馈；无常驻循环动画，尊重减少动态效果。
- 检查自动/浅色/深色、窗口失焦、减少透明度、增强对比度与 VoiceOver；正文与关键状态不能靠背景壁纸保证可读。

Apple 将 Liquid Glass 定位在控制与导航层，并建议克制使用；因此保留局部通透、加强正文稳定性更适合这个方向。[Apple 材质指南](https://developer.apple.com/design/human-interface-guidelines/materials)

## 实施顺序与验收

### 第一阶段 让待办成为主界面

交付任务主列表、导航壳、标题快速录入、可选估计时长、完成框/标题/专注按钮分离、⌘Z/恢复与最近删除、紧凑计时栏、基础搜索，以及浅深色和窄窗口适配。视觉规范从本阶段开始落实。

底层先分离列表选择与当前专注；定义任务存储接口、迁移与备份。完成历史不再占用 100 项待办额度；分批加载历史，替代粗暴删除或只修改上限数字。旧任务、截止日期、计时偏好和历史必须全部保留。

验收：仅输入标题即可连续添加；任务勾选、选中和计时互不误触；完成/删除均能恢复；运行计时中可以改其他任务；⌘B 后清单完整可用；升级及失败恢复不丢数据。

### 第二阶段 形成日常安排流程

交付收件箱/今天/接下来/全部、自定义清单、计划日期与 deadline 分离、仅日期截止、按 deadline/手动排序、备注、跨清单搜索、批量移动与完成、任务提醒，以及本机导出/导入。

验收：能把未安排事项加入今天；能查找跨清单任务；无截止日期任务不被误报逾期；改计划不改 deadline；提醒拒绝/改期/完成后均正确重排或取消；导出再导入保持 ID 与完成状态且不产生重复事项。

### 第三阶段 完善执行与系统入口

交付按事项关联的专注日志、每项实际投入时间、可选逐项队列、一级步骤清单、基础重复规则、菜单栏/全局快速录入。新增能力默认收起，主列表不增加固定属性列。

验收：重命名不切断日志关联；暂停与提前结束统计正确；队列不会自动完成任务；完成重复事项只生成一次下一条；重复规则、延期与恢复不会产生重复任务；全局快捷键可配置且不抢常见系统快捷键。

### 第四阶段 稳定发布与小组件

交付长期使用测试、辅助功能与快捷键复核、备份恢复演练、已签名的小组件实机验证及 README/演示更新。小组件默认今天清单，计时是次级状态；扩展仅读取所需快照。

验收：基于相同数据与窗口状态通过性能门槛；在实际安装版验证通知与小组件；不把未签名预览作为已完成的系统集成。

建议先做第一、二阶段，达到“无需打开时钟，也愿意每天用”的标准，再扩展第三阶段。阶段内可拆成独立可回退的提交，不把换存储、换布局、增加重复规则混成一次大改。

## 数据与低资源约束

当前全量状态会在事务中重新解码，`FocusModel.send` 同步调用存储；小数据量下合理，取消 100 项限制后需要调整。建议让任务、专注状态与展示状态分工，磁盘读写移出主线程且按顺序执行；使用稳定 ID、按需构建行、缓存筛选结果，避免每次倒计时变化触发全清单刷新。

数据模型逐步增加 `estimatedMinutes?`、`plannedDay?`、支持日期/精确时间的 deadline、`listID`、`completedAt?`、`deletedAt?` 与排序键。新专注日志保存任务 ID 和标题快照。旧日志缺失 ID，保留为历史记录，不按同名文本猜测归属；旧任务缺少创建/完成时间，保留未知值，不伪造时间。

迁移采用版本校验、升级前快照和临时文件验证后替换；失败保留原数据，旧版本拒绝写入新格式，App 与 Widget 一并升级。迁移、导入、撤销都需要验证正在运行的计时与跨进程写入。初期可以保留有界 JSON 活跃数据与分批归档；用千条数据实测后决定是否改为系统 SQLite。数据库本身不是低内存保证，避免在第一版同时重写所有层。

继续保持无 WebView/Electron、无后台网络轮询、无额外常驻服务。空闲/暂停不启动周期工作；提醒交给系统调度；倒计时只更新可见时间文本，截止状态在日期边界、激活或数据变化时重算。Widget 只在其所需数据变化时刷新。撤销栈与缓存有界，完成记录可以长期保存而不全部常驻内存。

**性能验收是提议的门槛，并非已达到的结果：**

| 场景 | 测量与门槛 |
| --- | --- |
| 基线 | 同一 Mac、优化构建、固定窗口/外观/数据；分别记录 10、100、1,000 项及大量完成归档的情形 |
| 内存 | 同时报告 RSS 与 physical footprint；小数据常用场景相对同条件基线增长不超过 15%，否则说明原因并优化；10,000 项用于压力诊断，不先承诺容量 |
| 长期运行 | 连续新建、搜索、展开、完成、撤销 100 轮后稳定占用；缓存预热后不能持续线性增长 |
| 空闲 | 5 分钟采样 CPU 均值目标小于 0.5%，没有任务级轮询或持续文件写入；关闭主窗口单独测 |
| 响应 | 1,000 项下普通操作反馈目标 100 ms 内，搜索目标 150 ms 内；记录 p95，并另测实际持久化完成时间 |
| 计时 | 运行、暂停、休眠唤醒和退出重开均不重复结算；任务编辑不重置当前计时 |
| 系统开销 | 材质评估也观察 WindowServer、唤醒次数与耗电，不只看应用 RSS |

仓库目前最近一次记录为 2026-10-05 的 0.6.0：特定两项待办场景 RSS 约 131 MiB、短时 CPU 0%。这是历史采样，不是 0.6.1 本轮新测结果，也不能据此声称领先竞品。详见 [资源占用记录](PERFORMANCE.md)。
